# Verification

This is the current test recipe. [catalog.json](catalog.json) is the complete fixture inventory: profile, command, prerequisites, mutation scope and purpose. [Workflow acceptance](../docs/workflow-acceptance.md) records executed revisions/environments. [Historical verification](../docs/history/verification-through-20261010.md) preserves the former long README and beta.1 receipts; those outcomes do not prove the current source.

## Portable entry point

Run from the repository root. Python 3.10+ coordinates native tools; PHP CLI, Node.js 22+, a POSIX shell and Chromium are required only by the selected group. Use PHP 8.3 for broad development fixtures; selected product-floor lifecycle checks support PHP 7.4, while other fixtures use newer APIs. Install pinned generator dependencies first:

```sh
python -m pip install -r tools/requirements.txt
npm ci --prefix tools
python tools/check.py fast --list
python tools/check.py docs
python tools/check.py syntax
python tools/check.py fast
python tools/check.py generated
```

`--php PATH`, `--node PATH` and `--shell PATH` select executables; repeat `--fixture NAME` for focused fixtures in `fast`, `wordpress` or `browser`. Other profiles reject fixture selections. `PROFILE --list` prints that group's available names. Profiles fail on missing prerequisites/unknown selections; skipped or unavailable execution is not a pass. Output is bounded; keep detailed failure receipts private and sanitized summaries in acceptance records.

The `php-dependency-reconstruction` fast fixture verifies the 219 pinned prefixed files, license inclusion and staging refusal without upstream Git history. Full reconstruction is a separate [development command](../docs/development.md): run it twice against the pinned release objects and compare exact output. No Composer install or runtime replacement occurs; neither fixture proves raw Composer/Mozart or unprefixed vendor reconstruction.

| Profile | Scope | Important prerequisites/boundaries |
| --- | --- | --- |
| `docs` | Local documentation links and repository configuration | Python; historical private receipt references are not public setup requirements. |
| `syntax` | Plugin/test/tool/CI PHP, JavaScript, Python and shell parsing, including shipped PHP dependencies; installed check-tool dependencies excluded | Applicable executables and `sh` (or `--shell PATH`); syntax does not replace static analysis or runtime tests. Workflow YAML was checked locally with actionlint; the current CI does not run that validator. |
| `quality` | Native PHP parsing, PHPCS and PHPStan on full changed maintained PHP files | Isolated locked `tools/php-quality` dependencies and PHP; Git revisions/local diff or explicit relative `--file` paths. Empty scopes skip analyzers visibly. |
| `fast` | Existing standalone regression fixtures using mocks/owned temporary files | PHP/Node as catalogued; no WordPress site, provider credentials or valuable runtime. |
| `generated` | Settings bundle and catalog consistency in a disposable copy | Pinned tool dependencies; validation does not rewrite the checkout. |
| `wordpress` | Native lifecycle/domain fixtures plus explicitly catalogued core-class models, serial per site | Native checks require a copied plugin, marked disposable site and separate database; focused `modeled-core` readers need a core copy without bootstrapping it. |
| `browser` | Chromium fixtures for settings/optimizer/worker behavior | `npm ci --prefix noobrocket/local-css`, explicit Chromium and any fixture-specific WP/PHP arguments. Synthetic form checks do not establish native page layout. |
| `server` | Owned Linux/MariaDB/Apache/Nginx/PHP-FPM/worker/multisite rehearsal | Linux dependencies, verified WordPress archive, unprivileged execution; owned service cleanup. |
| `package` | Existing ZIP structure/integrity and optional exact source equality | `--zip FILE`; `--compare-source` only for a ZIP intended to match the checkout. |

## PHP quality gate

Install only the isolated tool manifest; never use Composer install/update in `noobrocket/` for this gate:

```sh
composer install --working-dir=tools/php-quality --no-interaction --no-plugins --no-scripts --prefer-dist
python tools/check.py quality --base origin/cache-cache --head HEAD --php /path/to/php
python tools/check.py fast --fixture php-quality --php /path/to/php
```

The first adoption checks full changed maintained PHP files, including touched views, procedural code and deprecated callers. Shipped `vendor/`, `inc/Dependencies/`, `inc/classes/dependencies/`, `inc/vendors/` and `inc/deprecated/vendors/` are excluded from targets. PHPStan scans their symbols to understand maintained callers without executing WordPress or plugin bootstrap code. Explicit `--file` paths must name maintained PHP inside the checkout; they cannot opt a dependency into this gate or escape the checkout. No base selects local tracked/untracked changes. Empty scope reports `SKIP`; it does not establish analyzer execution.

PHPCS runs PHPCompatibilityWP with a PHP 7.4 floor plus selected WordPress rules for output escaping, POST nonce verification, validated/sanitized input, prepared SQL and the `noobrocket` gettext domain. These rules report errors and warnings as failures. GET nonce recommendations are outside this first gate: public cache admission also checks whether query inputs exist, without processing an admin mutation. Review and native boundary tests remain necessary for authorization, GET mutations and data ownership. Full inherited formatting rules are also outside this staged adoption.

The stable PHPCompatibilityWP/PHPCompatibility versions miss some PHP 8 syntax, including nullsafe access. The gate therefore first parses selected files with its actual `--php` binary; CI's existing PHP 7.4 job executes the quality fixture and integrated changed-file gate before WordPress setup. That native parser enforces the product syntax floor on all selected maintained files. A local PHP 8.3 gate alone cannot establish PHP 7.4 syntax compatibility; repeat it with `--php /path/to/php-7.4`. Native parsing does not prove every API call exists at the floor.

PHPStan runs WordPress-aware level 1 with `phpVersion: 70400`; no baseline or ignored-error patterns are loaded. It detects unknown functions/classes/methods and basic variable/control-flow errors. Level 1 does not prove strict argument/return types, and the installed recent WordPress stubs do not prove every called API exists in WordPress 5.8. Native minimum/current matrix checks remain separate. The retained upstream baseline names obsolete tests and is historical input, not an active suppression list.

The opt-in `php-quality` fixture executes actual tools in an owned copy: real Git revision/rename/staged/untracked scope, shallow merge-candidate failure and full-history recovery, base-side deletion with a diverged PR head, a seeded unescaped output failure, a separate undefined-call failure, nullsafe syntax rejection by PHP 7.4 (and the documented static-tool blind spot on PHP 8.3), a repaired probe and five maintained cache/CSS/preload owners. It fails on missing tools. CI fetches candidate history, compares its current base to the integration candidate, and runs this fixture before checking those changed files, so a documentation-only empty scope cannot masquerade as analyzer proof. No site, provider request or shipped dependency install is involved.

## Native WordPress safety

Install WordPress into an explicitly disposable root with its own database/site URL. Copy `noobrocket/` to `wp-content/plugins/noobrocket/`; a source junction is rejected. Create `.noobrocket-acceptance-site` only after confirming the installation may be mutated/destroyed. An existing localhost preview is not an acceptable lifecycle target.

```sh
python tools/check.py wordpress --wordpress /absolute/path/to/disposable-wordpress
```

The default group runs non-HTTP native activation/settings/update/branding proof serially, with activation first. Destructive phases such as `acceptance:deactivate`, `acceptance:uninstall` or `acceptance:collision` require explicit selection. The ordered destructive sequence is `acceptance:veto`, `acceptance:deactivate`, `acceptance:uninstall`, `acceptance:collision`, then `acceptance:restore`, following the initial activation phases. Restore removes only the exact owned `OtherCache` fixture contents, reactivates Cache-Cache and disables fixture CDN settings; it does not remove an unrelated drop-in. Inspect the catalog before selecting any phase.

The runner installs an owned temporary MU HTTP guard before WordPress boot and removes it after the sequence, including failures. It preserves synthetic fixture responses registered before the terminal `PHP_INT_MAX` guard and blocks real requests, including localhost, by default. Deliberate mocks use a lower priority, including `PHP_INT_MAX - 1`. A blocked request records a private marker without its URL; the completed check fails even when the fixture ignores `WP_Error`. Marker write failures fail immediately. Fixture HTTP guards disable Action Scheduler's automatic async loopback at shutdown; these checks exercise their own queue/worker actions without incidental dispatch. Explicit fixed-port HTTP scenarios first prove that port 8765 serves the selected copied site using a unique temporary probe file; only that verified origin is then permitted. A protected preview on that port fails the probe before site mutations. [wordpress-http-audit.php](wordpress-http-audit.php) remains optional diagnostic instrumentation that records destinations without query strings and allows localhost unless an explicit origin is configured; it does not replace the runner's stricter boundary. Its unexpected blocks also reach the runner's private marker. Do not install instrumentation into an existing site. Fixtures do not constitute provider-account testing.

HTTP/stale/local CSS fixtures additionally require the configured loopback server and pretty permalinks, plus any browser/worker argument listed in the catalog. Run all site-mutating checks serially. Parallel environments need distinct databases, paths and ports. Preserve owned failure logs; do not restore shared runtime rows to an old baseline.

`wordpress --fixture wordpress-database-transients` runs the actual database-cleanup worker with native WordPress option/transient APIs and a query boundary limited to uniquely owned names. It checks normal deletion, external-cache invalidation plus persisted timeout/value removal, absent timeout/cache keys, native hooks, matching displayed counts, SQL refusal and protected/unrelated rows. External-cache mode is toggled request-locally against WordPress's in-memory cache; this proves the native API branch, not a particular Redis/Memcached backend. `wordpress --fixture wordpress-database-transients-multisite` requires a real marked disposable network and adds one owned sibling site to verify site isolation; shared network option/cache entries remain intact. Both fixtures restore prior result storage and cache mode, remove only their owned rows/keys and never dispatch the cleanup queue. Existing `fast --fixture wordpress-database-cleanup --fixture wordpress-database-lifecycle` fixtures cover bounded resume, completion/cancellation and lifecycle ownership with modeled storage.

`wordpress --fixture acceptance:import-validation` seeds nonempty saved DNS/CSS/URL lists, then boots fresh PHP workers for the registered import handler and subsequent native notice consumption. It checks malformed-list feedback, retained fields, protected site/version identities, a valid sibling change and exact reviewed persistence, then restores the exact owned options value through `$wpdb` and removes its review/error receipts. Cleanup bypasses save callbacks that rotate CSS keys, clears the parent request's stale option cache and regenerates configuration/rewrite files. Ordinary cache, history and queue effects remain in the disposable site. Native WordPress nonce, capability, sideload, sanitizer, option/transient and notice-rendering APIs run; redirects are intercepted before exit. This CLI proof does not exercise a browser or an HTTP multipart request.

`wordpress --fixture wordpress-database-eligibility` invokes the registered cleanup owner with native post/comment APIs and deletion hooks. Exact owned-ID query boundaries preserve other rows while five selected categories are restored/approved after batch selection; explicitly reseeded stale object-cache entries ensure eligibility comes from the database. Actual SQL read refusal retains the row and records failure, and a 51-row keyset proves resume across changed/missing rows. The fixture restores prior cleanup result storage, removes only its owned posts/comments, never dispatches the queue and does not prove transactional isolation against changes after the eligibility read. CI selects it for the native minimum and current WordPress/PHP pairs.

## Browser and server proof

```sh
npm ci --prefix noobrocket/local-css
python tools/check.py browser --chromium /absolute/path/to/chromium --wordpress /absolute/path/to/wordpress-core
```

Keep Linux Chromium sandboxing enabled and run unprivileged. The default browser group needs an explicit WordPress core copy for native class readers without site bootstrap. Browser fixture prerequisites differ: some start synthetic loopback servers; others load WordPress classes or exercise the same-server generator. A focused fixture without `wordpress-core` can omit `--wordpress`. Select through the catalog instead of assuming every browser check needs a live site. [Worker documentation](../noobrocket/local-css/README.md) owns installation, origins, scheduling and recovery.

`browser --fixture preload-links-browser` runs the maintained readable and served minified link runtimes. It proves detached intent activation and native document Eager activation under CSP: the destination loads with `document.prerendering=true`, navigation has `activationStart>0`, and activation reuses one eligible request carrying prerender `Sec-Purpose`. Excluded destinations remain unloaded. Document mode uses an owned loopback debugger, attaches to the native tab target, then supplies trusted hover through its child page session. No browser policy or prerender feature override is used. A separate direct page-target case records `PrerenderingDisabledByDevTools`; that restriction does not prevent the tab-target proof.

Synthetic DOM mouse events do not establish native browser interest. [Chrome's prerender guide](https://developer.chrome.com/docs/web-platform/prerender-pages) documents Eager's 10 ms desktop hover since Chrome 143 and mobile viewport heuristics since January 2026. The desktop activation fixture does not prove mobile heuristics, every browser, or production-site activation.

The `server` profile delegates to [linux-production-proof.sh](../tools/linux-production-proof.sh):

```sh
python tools/check.py server --wordpress-zip /path/to/verified-wordpress.zip --php /path/to/php --node /path/to/node --chromium /path/to/chromium
```

The Linux script reads `PHP_FPM` and optional `APACHE_MODULE_DIR` from the environment; the runner sets `PHP_CLI` from `--php`. It creates owned disposable MariaDB/site/server paths and cleans only owned processes. Each Apache/Nginx listener proves it serves that site's unique temporary file before the audit permits its exact loopback origin. The harness checks the audit's sanitized blocked-request marker before reporting success, so ignored errors in direct PHP fixtures or web requests fail the completed rehearsal. CI site setup also rejects blocked requests during installation. Both installers supply their chosen pretty-permalink structure through a scoped option filter during `wp_install`, remove the filter in `finally`, then save the real option; this avoids core's speculative loopback discovery before a listener is authorized. Real server permalink delivery is checked after origin verification. Repository CI uses verified WordPress archives and isolated jobs; production Nginx configuration is not proved by a synthetic Windows proxy.

## Focused lazy-load proof

```sh
python tools/check.py fast --fixture inline-background-lazyload --php /path/to/php
python tools/check.py browser --fixture inline-background-lazyload-browser --php /path/to/php --chromium /path/to/chromium
python tools/check.py fast --fixture lazyload-bootstrap --php /path/to/php
python tools/check.py browser --fixture lazyload-bootstrap-browser --php /path/to/php --chromium /path/to/chromium
python tools/check.py wordpress --fixture wordpress-picture-delivery --wordpress /path/to/disposable-wordpress --php /path/to/php
python tools/check.py browser --fixture picture-delivery-browser --wordpress /path/to/disposable-wordpress --php /path/to/php --chromium /path/to/chromium
```

The inline-background fixtures exercise the bundled PHP owner and readable/minified 17.8.3 runtime at 1365×900 and 390×844. Layered, repeated and unsupported declarations remain byte-identical and eager; supported single URLs retain quotes, literal parentheses, unrelated declarations, exclusions and the actual Avada filter. Browser checks compare computed layers with the original CSS, verify eager requests and later single-URL intersection loading, and retain layered declarations with JavaScript disabled. WordPress helpers are modeled and image responses intercepted; these fixtures do not bootstrap a site or establish a loading-speed gain.

The bootstrap fixtures use actual footer/buffer subscriber output and shipped library bytes with modeled WordPress boundaries and intercepted browser responses. They do not bootstrap a site or contact providers. Default empty/target pages retain original HTML and work under a final CSP header added after PHP, including a later AJAX target. Optimization scenarios explicitly enable the default-false `noobrocket_lazyload_gate_runtime` filter; actual use requires final Nginx/CDN response policy permission for its inline bootstrap and accepts delayed `LazyLoad` globals/events. Known enforcing PHP/meta CSP still retains original delivery when opted in. The fixtures check opted-in empty/eager-only pages, dynamic targets, YouTube thumbnail timing, filtered configuration/runtime attributes, CSP/Trusted Types fallbacks, shipped DelayJS activation, fallback markup and bootstrap observer cleanup. Combine removal/relocation is modeled output; the fixture does not execute native combining. The existing native picture fixtures separately cover production responsive conversion, library activation and JavaScript-disabled fallback; both require a marked copied-plugin site and serial execution. These checks establish behavior and opted-in avoided runtime work, not a PageSpeed score or measured site-speed gain; no settings or deployment changes are performed.

## Meaningful proof and limits

`wordpress --fixture cache-purge-boundaries --wordpress /path/to/wordpress-core --php /path/to/php` loads actual purge owners and core filesystem classes without booting a site. Owned temporary files exercise parent-path rejection, Unicode/no-dots naming, public/user ownership, wildcard matches, injected deletion refusals and preserved hooks. Directory-link and literal-star directory controls execute on Linux; Windows reports explicit skips when its filesystem forbids them. This is native filesystem proof with modeled WordPress boundaries, not native site or concurrent-process proof.

`wordpress --fixture wordpress-cache-purge-boundaries` adds native WordPress bootstrap, administrator permission and Ability execution on a marked copied-plugin site. Unique cache entries prove rejected sibling paths/wildcard searches, refused deletion and successful device-cache deletion; Linux also executes linked-directory preservation. It compares installed purge-owner bytes to the candidate before bootstrap and removes only its owned entries. The minimum/current CI pairs select both fixtures; concurrent filesystem replacement remains outside this proof.

For cached beacon nonce expiry, select `fast --fixture beacon-nonce --fixture wordpress-performance-hint-boundary --fixture wordpress-beacon-collector-limits` and `browser --fixture beacon-nonce-browser --chromium /path/to/chromium`. The modeled check executes the shared AJAX subscriber/processor; the browser check runs both maintained readable and served minified assets with every request intercepted. It covers one shared refresh/retry budget for check/save, invalid envelopes/fields, HTTP/network failures, collector rejection and storage/no-op outcomes, plus aborted requests and late timer/collector/repeated initialization. Deadlines are invoked directly to make race proof deterministic; the fixture does not wait ten seconds or establish real database/WordPress HTTP behavior.

Native proof is opt-in: `python tools/check.py wordpress --fixture wordpress-beacon-nonce-http --wordpress /path/to/disposable-wordpress --php /path/to/php`, with the copied site served on port 8765. For another already owned loopback listener, invoke `php tests/wordpress-beacon-nonce-http.php /path/to/disposable-wordpress http://127.0.0.1:PORT` under the same existing external-HTTP guard. The fixture checks its marker, affected plugin bytes and a unique listener probe before booting the site. Actual core nonces from two ticks ago must produce HTTP 403/`-1`; registered guest/authenticated refresh must return uncached valid session nonces, and retries must persist completed SQL rows. Existing-row replies preserve stored data. The fixture uses one unique URL and a temporary subscriber/session, restores settings, and removes its rows/user in cleanup. It tests native endpoints/storage; the intercepted browser fixture owns the client retry budget and timer proof. Run site mutations serially.

The Linux server rehearsal also runs this native nonce fixture against its verified Apache/FPM listener on port 8875 before the network phase.

Run `fast --fixture revision-invalidation --php /path/to/php` and `wordpress --fixture wordpress-revision-invalidation --wordpress /path/to/disposable-wordpress --php /path/to/php` through `tools/check.py` for revision housekeeping. The modeled fixture invokes actual registered callback mappings with revision/autosave, parent, attachment, disabled-context and false-permalink controls; retained RUCSS is invoked defensively without activating its cloud path. The native fixture uses actual core revision retention pruning and autosave updates/deletion, monitors optimization/preload table queries during revision hooks, and checks real parent old/new page-cache files and hint/local-CSS/preload rows. It requires a marked copied-plugin site, restores prior table rows and blocks HTTP. A deleted revision ID cannot be recognized by `wp_is_post_revision()` after its row/cache entry is gone; the existing missing-permalink exit then prevents optimization work. Native permalink filters establish no generated revision URL, not zero generic WordPress helper calls. These checks do not measure cleanup throughput or visitor performance.

Run `wordpress --fixture wordpress-query-cache-invalidation --wordpress /path/to/disposable-wordpress --php /path/to/php` for the bundled BerlinDB result-cache regression. The marked copied-plugin site receives one owned suffixed table and version option, removed in `finally`; HTTP is blocked. Actual query instances exercise a cached miss followed by insertion, update and deletion with reused and distinct writers. SQL probes verify complete repeated reads stay cached and missing item rows require one priming SELECT without changing the result generation. The fixture compares the installed Query owner with maintained source before bootstrap. This is native mutation visibility and request-local cache proof, not persistent-cache backend concurrency or visitor-speed measurement.

`wordpress --fixture wordpress-bootstrap-construction` exercises all five maintained schemas with native WordPress sanitizers, complete metadata comparison, template reuse, distinct column/validator objects, first-caller mutation isolation, changed definitions/hook/database context and per-construction custom-filter fallback. It also resolves actual settings/preload services and runs nested read-only preload queries with independent mutable state. `wordpress --fixture wordpress-bootstrap-construction-multisite` requires a real marked disposable network and adds one owned temporary blog to prove the shared preload table follows switch/restore while queries remain independent; it removes that blog and restores context. These checks establish avoided repeated construction and preserved behavior; matched native timing remains necessary for a speed claim.

For direct multisite execution, supply the owned network's host and port so WordPress selects the intended site, for example `HTTP_HOST=127.0.0.1:8875 /path/to/php tests/wordpress-bootstrap-construction.php /path/to/disposable-wordpress multisite`. Substitute the network's actual host/port. The fixture preserves that host, derives the port and rejects premature bootstrap exits through its completion guard; an early redirect is not a passing check.

`wordpress --fixture wordpress-preload-discovery` requires a marked copied-plugin site on MySQL/MariaDB and `proc_open`. It creates its own suffixed preload table/version option and runs two separate PHP processes, synchronized after their first URL lookup, against actual database/query owners. It checks atomic normalized insertion, winning-row recovery, full URL identity, filtered URLs, nullable legacy metadata, failed/partial migration retry and collision isolation. It also removes an owned row between ID selection and item shaping, and supplies invalid items through the native result filter with warnings promoted to exceptions; that deletion timing is controlled in one process, separately from the actual two-process insertion proof. The fixture drops only its owned table and retains subprocess evidence on failure. SQLite does not establish native MySQL concurrency. The minimum-version CI pair explicitly selects this fixture; the current pair includes it in the default native group. The proof does not measure contention frequency, large-table DDL cost or visitor speed.

For sitemap traversal, run `fast --fixture preload-sitemap-traversal` and `wordpress --fixture wordpress-preload-sitemap-traversal --wordpress /path/to/disposable-wordpress`. The native fixture verifies registered callbacks, actual scheduler jobs and page storage in a marked copied-plugin site; it removes only its owned jobs/row and mocks all sitemap HTTP. CI selects it for minimum/current WordPress pairs. Neither fixture establishes cross-parent deduplication, URL alias detection, multi-node cycle prevention, simultaneous workers or crawl throughput.

For stylesheet-background publication, run `fast --fixture stylesheet-background-publication`, `browser --fixture stylesheet-background-publication-browser --php /path/to/php --chromium /path/to/chromium`, and `wordpress --fixture wordpress-stylesheet-background-publication --wordpress /path/to/disposable-wordpress --php /path/to/php` through `tools/check.py`. The native fixture uses the registered extraction/transformation/tag pipeline on a marked copied-plugin site; it does not need a listener or real provider requests. Modeled interleaving is not simultaneous-process proof, and browser-cache reuse is not a measured whole-site speed improvement.

`local-css-stylesheet-boundaries` exercises actual local CSS selection and completed delivery with modeled WordPress/job storage and one owned temporary stylesheet. `local-css-stylesheet-boundaries-browser` supplies that owner's manifest to the actual used/critical generator at 1365×900 and 390×844 on an owned loopback listener. The checks cover inert template/raw-text/attribute bytes, real base/head boundaries, exact offsets and existing exclusions. Trace failures to native owners and add a regression that fails for the defect while preserving surrounding behavior. Test helpers/instrumentation are catalogued but are not automatically runnable tests. A modeled fixture can exercise real plugin classes without booting WordPress; label it accordingly. Do not advertise absent upstream PHPUnit/PHPCS/PHPStan suites or call parsing static analysis.
