Settings notifications

Standalone Cache-Cache notices appear in one tray at the lower right, above the Save controls. Success, error, warning and information have distinct colors, icons and translated labels. Failed homepage probes are errors; a successful response without a cache-hit header is a warning, because static delivery can bypass PHP.

Errors, warnings, recovery actions and ongoing processes remain available. Completed outcomes remain visible until dismissed or the document is left. Recovery links, cleanup lists and readonly configuration stay intact. Notices that require recovery retain their original dismissal policy. Field validation stays in its settings context. Without JavaScript, native notices and their actions remain visible.

PageSpeed Insights checks

In Overview, open the PageSpeed API key setup. Enable the PageSpeed Insights API in your Google Cloud project, then create an API key and save it. Restrict the key to that API. Requests come from your WordPress server: use its outbound IP for an IP restriction; browser referrer restrictions do not fit this integration.

Run Mobile or Desktop to check your public homepage. Each check shows Performance, Accessibility, Best practices and SEO scores, plus lab loading metrics and the check time. Results vary with test conditions and do not represent real-user field data. Google cannot reach localhost or private previews.

The key stays on your server and is excluded from settings exports and history. The input remains blank when a key is configured; enter a new key to replace it. Removing the key preserves previous results. Failed checks also preserve the previous result. Checks do not save pending optimization settings or purge cache. No automatic checks are scheduled. Uninstall removes the key and saved results.

For rejected keys, check that the API is enabled in the owning project and that restrictions allow server requests. For quota errors, check Google Cloud quotas and retry later. For analysis failures, make sure the homepage opens publicly without a login or bot challenge.

Page cache and background refresh

Use Settings → Cache-Cache to configure page caching and preload. Deactivate other page-cache plugins before activation: WordPress has one shared advanced-cache.php slot.

PHP cache hits send Cache-Status: NoobRocket; hit. Logged-in users, private previews and unsupported query strings bypass the public cache. Static server delivery has its own rules and headers.

Background refresh keeps supported public pages for at most one hour after their configured lifespan while native preload refreshes them. Enable preload and a nonzero cache lifespan first. Legacy WebP variants and mandatory/dynamic cache cookies are incompatible with this mode. Content changes and manual purges remain immediate.

With background refresh enabled, route page requests through WordPress PHP. Apache direct HTML rules are omitted automatically. Nginx operators must disable direct page-cache rewrites; a static server or independent proxy cache cannot enforce the PHP deadline. Run WordPress cron regularly.

Local critical and used CSS

Choose Original CSS, Critical CSS or Used CSS in CSS & JavaScript. Install the bundled worker's dependencies with npm ci --prefix /path/to/noobrocket/local-css. The generator needs Node.js and Chromium on the WordPress server or VPS.

Run node /path/to/noobrocket/local-css/worker.mjs --wordpress /path/to/wordpress --site-url https://example.com/ --check to verify prerequisites. Schedule bounded worker batches under a user that can read WordPress configuration and write plugin cache files. On multisite, select and schedule each site separately.

See the bundled worker guide for browser/PHP paths, scheduling, job limits, trusted asset origins and recovery. Original styles remain active until a valid result is published. Safelist selector substrings for interactive or dynamically inserted content. Test menus, dialogs, forms, carts and mobile layouts.

AVIF and WebP images

Modern image delivery wraps eligible local images in native picture markup, preferring AVIF, then WebP, with the original image as fallback. Browsers choose the format; the HTML cache is independent of the Accept header. This works with ordinary Nginx static page delivery.

Use the dashboard to generate derivatives for the existing media library. New uploads are queued automatically. Encoding uses WordPress's native image editor and the formats supported by the host's GD or Imagick installation. Processing is bounded to four encodes per cron invocation, with a twenty-second soft deadline.

Original files and externally generated derivatives are preserved. Owned derivatives refresh when source bytes change. A completed scan purges page cache once. Interrupted scans resume. Uninstall preserves generated images because cached HTML may still reference them.

Enable delivery on staging first: adding a picture wrapper can affect theme selectors such as .hero > img. Complete responsive families are required; unsupported or missing derivatives retain the original image.

Asset Manager and settings history

Open the Asset Manager tab in Settings → Cache-Cache. Inventory a selected page using your private preview, then draft rules by CSS/JavaScript handle. Rules can target all pages, a post, post type or template, with explicit post exceptions.

Preview saved draft opens in a separate tab and retains unsaved settings and rule input in the editor. It uses the saved private draft and affects only your authenticated request. Retained assets keep their recursive dependencies. Publish the reviewed draft to affect visitors. Hardcoded tags and unmanaged inline assets are outside the handle-based manager.

The last five settings/rule snapshots can be restored through the same native save path. Credentials, cache keys and version markers are excluded. Preview is not a full-site simulation of every optimization setting.

Object-cache setup and troubleshooting

Cache-Cache uses WordPress's existing object cache. Without an external provider, WordPress keeps cached objects only for the current request. To retain objects between requests, configure a supported provider through your host or its WordPress plugin, following that provider's setup guide. Cache-Cache does not install Redis, Memcached or an object-cache drop-in.

The Overview card identifies the current provider and tests one temporary key by writing, reading and deleting it. A successful check proves operation in that request; it does not prove persistence between requests. Cache-Cache never performs a global object-cache flush as part of this check.

If the card reports “Needs attention”, inspect the provider's connection status, service availability and configuration. Use its own diagnostics to verify persistence. Reload Overview after recovery. If “Request local” appears when you expected persistence, confirm that your provider is enabled and that WordPress loads its wp-content/object-cache.php drop-in. Avoid replacing a provider's files or clearing unrelated application caches to fix a Cache-Cache status card.

Next-page loading

Open Preload → Next-page loading. Link preloading downloads eligible HTML after link intent. Prerender public pages prepares the full page invisibly using the browser's Speculation Rules API. Prerendering defaults off. Link preloading retains its saved choice and is enabled on new installations. The options can be saved independently. Prerendering improves later navigation, rather than the first visit, and works alongside PHP or Nginx page caching.

One destination is prepared at a time after hover, keyboard focus or press intent. Prerendering loads resources and runs JavaScript before the click, using more bandwidth and memory. Compatible browsers fall back to HTML preloading. Data Saver, slow connections and browsers unable to evaluate required exclusions use normal navigation.

Only public anonymous contexts are eligible. Native WordPress, cache and preload exclusions are honored alongside common login, checkout, account, search and action routes. Query/fragment links, downloads, non-document files, other origins, new windows and nofollow links are skipped. Add your site's custom private/action routes under Prerender exclusions, one URI pattern per line, such as /members/(.*). Add no-prerender, no-prefetch or data-noobrocket-no-speculation to a link or its ancestor to opt out.

WordPress's native configuration opt-out is respected. When Cache-Cache owns prerendering it suppresses the broader default core rule; disabling the option preserves native core behavior. Dynamic rules inherit the handler's CSP nonce. Analytics and visit-dependent scripts should wait for activation; see browser activation guidance. Check representative public pages and their analytics before enabling this on a live site.

Other optimizations

CSS & JavaScript includes optional removal of anonymous Dashicons, dormant embed assets and unused block-library styles. These controls default off and preserve known WordPress dependencies and block content.

Use your own CDN CNAMEs for URL rewriting. Start with one optimization at a time, save, purge affected cache and check representative pages. Database cleanup should be used with a current database backup.

Troubleshooting and lifecycle

  • For unexpected layout or scripts, disable the relevant optimization, save and purge cache. Check the original page with the nonoobrocket=1 query parameter.
  • Use dashboard worker diagnostics for missing prerequisites or failed CSS jobs. Keep the original styles while recovering generation.
  • Verify server routing and permissions when the page cache stays cold. A filesystem purge cannot invalidate a separate proxy/CDN cache automatically.
  • Deactivation preserves settings. Uninstall removes owned settings, queues, tables and cache directories; another plugin's data remains untouched.
  • Install updates by uploading a verified Cache-Cache ZIP. No remote update or rollback service is configured.
