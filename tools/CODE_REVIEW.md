## Inventory and review method

The pre-rename source inventory contained 1,409 plugin PHP files. Comparing paths with `base-wp-rocket/` classified 24 PHP files as additions and 287 as different after coarse product-name normalization. The comparison replaced WP Rocket/Rocket and NoobRocket names before comparing text; it also tried renamed filenames. Namespace, generated loader and filename differences can affect these counts. They measure the comparison surface, not verified behavior or exhaustive line coverage.

Detailed review followed active registration from `noobrocket.php`, `inc/main.php` and `inc/Plugin.php`, then traced settings, frontend buffers, cache paths, purge/preload and deactivation/uninstall. New Assets, Bloat, ObjectCache, Picture and LocalCSS modules received direct source review. Local CSS JavaScript generation and its same-server bridge were checked at their PHP/browser boundary. Inherited minification, lazy loading, CDN rewriting, native fonts, authentication cache gates and WordPress dependency handling were reviewed where new modules interact with them. Composer and bundled dependencies were inspected for namespace/loading and ownership boundaries; this review does not claim a new security audit of every third-party library.

Changes use existing WordPress options, hooks, capability/nonce checks, queues and cache ownership conventions. Focused regression fixtures precede or accompany fixes. PHP mocks prove the specified API contracts and real temporary-file operations; actual WordPress/HTTP/browser fixtures establish the corresponding integration behavior when run. A fixture filename alone is not evidence that its latest revision passed.

The final readability cleanup expanded compressed methods, guards, loops, callbacks and service registration in LocalCSS's `Frontend.php`, `Subscriber.php`, `ServiceProvider.php`, `Jobs.php` and `Diagnostics.php`, with property docblocks and aligned event mapping. ## Cache and loading performance conclusions

The strongest concrete hot-path improvement is direct delivery of the already generated gzip file. Its benefit must be reported as measured transfer bytes and CPU avoided on that branch, not as an unmeasured site-wide LCP gain. WordPress HTTP clients can transparently decompress responses, so decoded-body equality alone cannot prove compressed wire delivery; use raw HTTP evidence.

Cache publication now adds a short nonblocking filesystem mutex for each variant. A request that loses the mutex keeps its rendered response and lets the current writer publish. Stable empty lock files live under `pages/.locks/`, outside host directories purged by TTL, so unlinking an active lock cannot create a second independent mutex. Uninstall removes them with the page-cache tree. This disk bookkeeping addresses the reproduced writer race; it is not a cold-request database stampede lock. Twenty-process proof establishes final publication consistency, not elimination of parallel WordPress rendering or a transaction spanning every concurrent reader.

The image queue remains bounded to four encodes and a twenty-second soft deadline per cron invocation. Originals and externally owned sidecars remain available. A completed scan clears page cache once, so earlier warm pages can retain old delivery until that scan finishes. An interrupted scan remains resumable. Image hashes now have a concrete purpose: source freshness and protecting external replacements at overwrite/deletion boundaries.

Stale refresh uses the existing Action Scheduler preload queue. Its one-hour grace is restricted to supported anonymous canonical variants; it requires preload and a nonzero lifespan and excludes mandatory/dynamic-cookie and legacy WebP variants. Manual/content purges remain immediate. Apache direct HTML rewriting is omitted while active. Nginx or an external CDN can bypass PHP's deadline; operators must follow [cache behavior](../README.md#cache-behavior) and verify the actual delivery path. A cron delay may postpone a refresh but must not extend the PHP cutoff.

The final stale-refresh seam passed 35 direct PHP assertions plus six native preload child assertions, and 37 isolated Nginx proxy assertions plus six child assertions, after the gzip patch. Environment: Windows PHP 8.3.35, WordPress 7.1.3, SQLite Database Integration 3.0.2 and Nginx 1.26.3 proxying to the marked PHP test server. Proxy proof establishes routing and cutoff, not native PHP-FPM compatibility. The daemon was stopped and fixture site/cron/action state restored; see the verification record in [tests/README.md](../tests/README.md).

LocalCSS completion retains original styles on pending/failed jobs and validates the submitted stylesheet manifest. Its result fingerprint covers mode, stylesheet URLs/media and safelist, not arbitrary HTML mutations. Existing content/settings/theme/purge hooks therefore remain necessary for freshness. New DOM-producing optimizations require explicit integration review, as the picture finding demonstrates. Conditional/dynamic states absent from the browser sample still require staging interaction checks and appropriate safelisting; adding more generic pruning is not justified by this review.

The existing matched comparison in [BENCHMARKS.md](BENCHMARKS.md) used 36 proven-hit samples per product with CSS generation disabled and a fixed theme. It found near-equivalent LCP and CSS transfer. It does not prove NoobRocket is faster than WP Rocket, and it cannot quantify the new gzip path or new optimization settings. Repeat a matched staging comparison after the final release candidate is stable; keep content, theme, settings, browser and hit state fixed.

The recorded 1.2.0 target-site proof also found duplicate native font CSS, adding an estimated 421 compressed bytes to the captured head without duplicate font downloads, plus retained Google noscript/discovery markup. This is a measured small follow-up candidate, not a reproduced defect in every installation or the current release. Recheck it on the final candidate before changing font delivery; preserving no-JavaScript and explicit native font fallback matters more than removing a small unmeasured duplication everywhere.

No additional persistent-cache backend, remote optimization service or general logging framework is required by these findings. Object-cache diagnostics check the already configured provider through one short-lived owned key and targeted deletion; a successful same-request probe does not establish cross-request persistence.

### Shared behavior and architectural decisions

Seven primary concepts replace the flat collection of settings destinations: Overview, Cache, CSS & JavaScript, Media, Asset Manager, Delivery and Maintenance. Secondary destinations appear within the active group. Existing hashes, hidden integration conditions, browser Back and filter-provided routes remain supported. The existing PageManager reads native integration checkbox state before delayed jQuery menu styling, so disabled initial or stored routes cannot briefly open. It also respects dedicated hidden menu entries without rejecting ordinary collapsed groups. The mockup's six concepts gain Asset Manager because it is an implemented feature with its own inspect/preview/publish workflow. Native destinations remain distinct so existing forms and integration conditions keep clear ownership.

Each visible route has a focusable h1. Page navigation and the plugin skip link move focus to that heading. Invalid required controls reveal their owning route and ancestor disclosures before native browser validation focuses them. Forms retain the original names, values, nonces and submitters; closed disclosures do not disable or discard their fields.

The settings form remains one native WordPress options form across pages. Dirty state compares current FormData with the initial form, so reverting a draft returns to clean. Its footer becomes available even on an action page if another page has dirty settings. Saving marks the form busy and blocks repeated submission. “Settings saved” requires WordPress success evidence; the query string alone cannot manufacture success. Independent forms and same-window admin-post links confirm discard before sending their requests. The browser's unload warning alone was insufficient for action links because the action request can execute before a navigation warning. Hash navigation, new tabs, modifier clicks and documentation links keep their normal behavior; ordinary leaving uses the native unsaved-change warning. This shared-form behavior is an intentional adaptation of the mockup's simulated per-screen save feedback.

Advanced fields use native `details`/`summary`; cleanup uses native `dialog`, with a confirmation fallback for older browsers. Existing PageManager, renderer, parent-field behavior and PHP handlers own the changes. There is no new router, state store, pagination service or duplicate save endpoint. The generated settings JavaScript is updated with its maintained source. Translations remain English gettext keys plus PO/MO catalogs; the updater contains no target-language dictionary.
