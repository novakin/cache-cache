## Retained boundaries

Previous CACHE-01–09 protections remain present: public early hits stay outside full WordPress bootstrap; private early delivery requires native authentication and is bypassed when unavailable; explicit private/no-store response directives prevent publication; executable policies publish atomically and require their completeness marker; public/user directory ownership is exact; refresh enters the existing pending table; scheduler admission uses native pending/running counts; the demonstrated composite SQL index remains; automatic discovery checks exact site origin and path.

The cache writer retains per-file locks, complete temporary-file publication and old-gzip removal after failed gzip replacement. Native content/manual invalidation still deletes immediately. PHP applies the hard stale deadline independently of cron. Apache omits direct HTML rewrites for stale refresh. Nginx remains operator-managed: the bundled guide requires routing through PHP and disabling direct page-cache rewrites for that mode. A static Nginx hit cannot enforce PHP policy or freshness.

No new cache service, scheduler, catalog, constructor graph, lifecycle event, SQL migration or general filesystem adapter was added. New helpers live in owners of the two shared invariants: published-file readiness and affected-blog deactivation scope.

## Material limits

The expiry filesystem walk remains proportional to the owned cache tree. The existing 50k-URL/200k-file Windows profile recorded about 11–12 seconds; this reaudit does not claim a new scan or visitor-latency measurement. Scheduler admission stays bounded, but traversal and pending-row touches remain a measured follow-up. A naive cutoff would starve tail directories, so no speculative persistent traversal mechanism was added.

The new lifecycle fixtures use actual policy files and cleanup owners but modeled WordPress blog/cron/Action Scheduler state. Installed multisite Action Scheduler cancellation, independent site activation, mapped domains, persistent object-cache contention and production PHP-FPM/server delivery need a separately owned native runtime proof. Existing broad Linux server proof remains historical and was not rerun against a valuable runtime. No production p95, FCP/LCP/CLS or matched competitor claim follows from these checks.
